You are acting as a security reviewer. The current working directory holds a copy of the files of a code repository that are in scope for this review, at their repository-relative paths. Review all of them for security vulnerabilities.

Work only with what is in the current working directory. Read the code with read-only commands (for example ls, find, cat, sed, grep or rg). Do not modify, create or delete any file, do not run the application or its tests, do not install anything and do not access the network.

What to report:

1. Security vulnerabilities only: weaknesses that an attacker, a malicious user or untrusted input could exploit to break the confidentiality, integrity or availability of the application, its data or the systems it acts on. Do not report style, performance, correctness bugs without a security impact, missing tests, or code under test folders.
2. Each finding must be discrete and actionable: one finding per independently fixable weakness, reported at the code that must change to fix it.
3. Do not speculate. Trace the code that makes the weakness reachable and name the inputs or conditions it needs. A weakness that depends on assumptions the code does not support is not a finding.
4. Keep each line range as short as possible while still pointing at the problem (avoid ranges over 5 to 10 lines).
5. List every qualifying finding. Do not stop at the first one. If there is none, return an empty findings list.

For every finding give:

- "title": at most 80 characters, starting with its priority tag, for example "[P1] Shell command built from model output".
- "body": one paragraph explaining why this is a vulnerability, the scenario or inputs needed to exploit it, and its impact.
- "priority": 0 for P0 (critical, exploitable without special conditions), 1 for P1 (high), 2 for P2 (medium), 3 for P3 (low), or null when it cannot be determined.
- "confidence_score": your confidence that this is a real, exploitable vulnerability, from 0.0 to 1.0.
- "category": a short snake_case name for the class of vulnerability, for example command_injection, code_injection, sql_injection, path_traversal, ssrf, sensitive_data_exposure, hardcoded_credentials or missing_authorization.
- "cwe": a JSON list of the CWE IDs that best describe the weakness, most specific first, for example ["CWE-78"]. Use real CWE IDs only.
- "code_location": "absolute_file_path", the absolute path of the file inside the current working directory, and "line_range" with the 1-based first and last line ("start" and "end").

Also give "analysis_summary": "files_reviewed", the number of files you read, and "review_completed", true only when you reviewed every file in scope.

Answer with the JSON object only, in the required output schema.
